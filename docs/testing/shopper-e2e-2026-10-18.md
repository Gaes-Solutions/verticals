# Comprador y recuperación: E2E con Next, API y DB reales

La pasada final terminó con **22 grupos aprobados**: 12 del comprador, 8 de
recuperación y 2 de teclado en cuenta autenticada. Se ejecutó sobre el build Next
final de esta auditoría y una base PostgreSQL local creada para la prueba.
No se interceptan respuestas del negocio ni se reemplazan componentes de la app.

## Repetir

Desde la raíz, con Node >=22.12, PostgreSQL local y un build vigente de web-tienda:

```bash
pnpm exec dotenv -e .env -- node scripts/testing/run-platform-workflows.cjs --shopper-e2e
```

El runner rechaza una base remota y puertos ocupados. Crea una DB `qa_platform_*`,
aplica migraciones, prepara el tenant `test-e2e-shopper` y levanta API 3059 y
Next 3058. Next usa `NODE_ENV=production` y API usa `test`. Genera una llave de
servicio local aleatoria; elimina keys de correo, pagos y otros proveedores del
entorno heredado. Los tokens de recuperación se guardan hasheados en la DB; los
datos necesarios para conducir el navegador viven en un archivo temporal privado.
El bloque `finally` cierra los procesos y elimina la DB tanto al aprobar como al
fallar una aserción.

## Evento de hidratación conservado para revisión

Una pasada anterior con el mismo build emitió React418 al recorrer/recargar el
carrito (`/tmp/gaes-shopper-e2e-final.log`). Se encontró y corrigió una inconsistencia
del harness: Next start heredaba `NODE_ENV=test` del runner de API. Dos pasadas
posteriores con Next en producción sumaron 18 recargas sin reproducir ese error;
la última aprobó el recorrido completo. La primera de esas dos paró después por
una guardia del test que bloqueaba la lectura automática de passkeys; se permitió
únicamente esa lectura documentada antes de repetir el ciclo completo.

Esto no establece la causa raíz del 418 ni supone una corrección en el código del
carrito. No se suprimió el error, no se modificó fuente para ocultarlo y las
aserciones de errores JS permanecen activas.

Estos resultados prueban los recorridos descritos en el entorno local aislado;
no certifican envío real de correo, proveedores de cobro, dispositivos físicos ni
el producto al 100 %. ST-007 conserva pendiente la validación publicada contra la
revisión `323bf8c` antes de cerrar su casilla. ST-006 es mejora de filtros móviles y
ST-010 conserva mantenimiento estructural de lint, según el backlog.
